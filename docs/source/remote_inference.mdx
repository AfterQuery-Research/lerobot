# Remote Policy Inference

Remote inference runs `lerobot-policy-server` on a GPU machine and
`lerobot-rollout` on the computer attached to the robot. The server owns the
checkpoint and model-side processors. The robot computer owns cameras, local
safety checks, action scheduling, and motor communication.

## Install

On the policy server:

```bash
uv sync --extra remote --extra molmoact2
```

On a dual-YAM robot computer:

```bash
uv sync --extra core_scripts --extra remote --extra bi_yam --extra intelrealsense
```

The `bi_yam` extra pins the tested i2rt commit. Its native `ruckig` dependency
uses the repository's `scikit-build-core` build constraint.

## Start a MolmoAct2 server

The released dual-YAM checkpoint contract uses normalization tag
`yam_dual_molmoact2`, three cameras in `top`, `left`, `right` order, and 14
state/action values in left-arm-then-right-arm order.

```bash
uv run lerobot-policy-server \
    --policy.pretrained_name_or_path=allenai/MolmoAct2-BimanualYAM \
    --policy.policy_type=molmoact2 \
    --policy.norm_tag=yam_dual_molmoact2 \
    --policy.model_dtype=bfloat16 \
    --policy.inference_action_mode=continuous \
    --policy.device=cuda \
    --host=0.0.0.0 \
    --port=8081
```

The server loads and warms the model before listening. Opening a session also
warms the exact camera dimensions and task prompt before the client is allowed
to arm the robot. Only one robot session is accepted at a time. The client only
needs the server's reachable IP address and port.

For a production deployment, add `--policy.revision=<commit SHA>` and use the
same expected model ID on the client so a moving Hub branch cannot change the
loaded checkpoint during a later restart.

## Test with the dual-YAM simulator

Run the shared-world MuJoCo simulator, replacing `<server-ip>` with the policy
server's reachable IP address:

```bash
uv run lerobot-rollout \
    --strategy.type=base \
    --inference.type=remote \
    --inference.server_address=<server-ip>:8081 \
    --inference.requested_model_id=allenai/MolmoAct2-BimanualYAM \
    --robot.type=bi_yam_simulator \
    --robot.backend=mujoco \
    --task="pick up the object" \
    --fps=30 \
    --duration=30 \
    --return_to_initial_position=false
```

Use `--robot.backend=fallback` for deterministic CPU-only dynamics when MuJoCo
or its renderer is unavailable. Both simulator backends expose the same policy
schema as the physical adapter. Simulation validates transport, timing, camera
ordering, action limits, and lifecycle behavior; it does not validate CAN bus
timing, camera placement, calibration, payloads, or physical collision safety.

## Probe real cameras without controlling the robot

`lerobot-policy-probe` opens only the configured RealSense cameras, submits one
observation, validates the returned action chunk, and discards it. The command
does not construct a robot, import i2rt, open a CAN interface, arm motors, or
persist action values. State is an explicit argument because obtaining live YAM
state through i2rt requires motor communication and belongs in a supervised
hardware test.

For a camera, network, and checkpoint smoke test, the released checkpoint's
median state can stand in for live state. Keep the source label accurate:

```bash
uv run lerobot-policy-probe \
    --server_address=<server-ip>:8081 \
    --task="pick up the object" \
    --state_source=checkpoint-q50-not-live-hardware \
    --state='[-0.07460957,1.45187420,1.27903396,-0.80040099,0.11633919,-0.22562396,0.74105157,0.08125296,1.54637449,1.24736453,-0.68268310,-0.13268824,0.19324336,0.69752937]'
```

Each run creates a timestamped directory under `outputs/policy_probe` containing
the three captured PNGs and `report.json`. The report contains frame hashes,
model identity, timing, action shape and range, and `actions_discarded: true`; it
never contains the action vector. This probe verifies real camera input and real
policy execution, but not live joint-state acquisition or physical control.

## Run a physical dual YAM

Configure the two CAN interfaces and verify each arm independently before
autonomous rollout. The physical adapter starts one isolated i2rt worker per
arm and keeps both workers idle until server negotiation succeeds.

The registered `afterquery_dual_yam` robot type provides typed defaults for the
lab installation: `can_yam_new` on the left, `can_yam_old` on the right, the
verified RealSense serials at 30 FPS (`top` at 640x480; `left` and `right` at
640x360), per-tick deltas of 0.03 radians for joints and 0.03 normalized units
for grippers, the lab's measured raw gripper endpoints canonicalized to the
active encoder period, and a one-second command watchdog. The policy deltas
admit the released checkpoint's small absolute targets while operational joint
and gripper bounds remain enforced. The watchdog
allows for normal three-camera scheduling jitter but still puts both workers in
safe idle if the client command stream stops. Server address, task, and duration
remain runtime arguments.

Like the original MolmoAct2 YAM launcher, this preset automatically moves to the
checkpoint's canonical start position before policy control: left arm joints at
zero with its gripper at `1.0`, then right arm joints at zero with its gripper at
`0.0`. The reset interpolates absolute waypoints approximately `0.01` apart at
30 Hz, holds the final target, and verifies every joint is within `0.03` of the
target. It aborts and idles both arms if the pose is not reached within 30 seconds.
The episodic strategy repeats this reset before every policy episode. With
LeRobot's default `--return_to_initial_position=true`, teardown parks at the same
canonical pose.

An i2rt `linear_4310` gripper without raw `[closed, open]` endpoints normally
performs a moving calibration while the robot is constructed. The AfterQuery
preset includes the measured endpoints, so normal rollout never calibrates while
connecting. If a gripper is serviced or replaced, recalibrate it separately under
supervision by explicitly clearing that stored override. Each command below
intentionally moves only the selected gripper:

```bash
uv run lerobot-calibrate \
    --robot.type=afterquery_dual_yam \
    --robot.calibration_side=left \
    --robot.left_arm_config.gripper_limits_override=null \
    --robot.left_arm_config.allow_gripper_calibration=true

uv run lerobot-calibrate \
    --robot.type=afterquery_dual_yam \
    --robot.calibration_side=right \
    --robot.right_arm_config.gripper_limits_override=null \
    --robot.right_arm_config.allow_gripper_calibration=true
```

The two commands merge their results into the standard LeRobot calibration file
for robot ID `afterquery_dual_yam`; copy the newly measured pairs back into the
typed preset before relying on a standalone checkout. Calibration mode starts
only the selected arm, does not open cameras, and disables policy control. Do not
set `allow_gripper_calibration` during an autonomous rollout.

```bash
uv run lerobot-rollout \
    --strategy.type=base \
    --inference.type=remote \
    --inference.server_address=<server-ip>:8081 \
    --inference.requested_model_id=allenai/MolmoAct2-BimanualYAM \
    --robot.type=afterquery_dual_yam \
    --task="pick up the object" \
    --fps=30 \
    --duration=60
```

After server negotiation succeeds, this command arms the robot and immediately
starts the canonical reset trajectory before sending any observation to the
policy. Clear the workspace and keep the hardware stop ready before launching it.

The generic `bi_yam_follower` type remains available for other installations;
its channels, cameras, and any explicit gripper overrides can be supplied with
normal dataclass-backed CLI arguments.

Camera dictionary order is part of the model contract. A missing, extra, or
reordered camera, state field, or action field makes session setup fail before
the robot arms. Commands are bounded by joint, gripper, and per-step delta
limits on the robot computer.

## Failure behavior

The client validates the protocol version, model fingerprint, exact feature
order, camera dimensions, and fixed task before arming. It uses one in-flight
request, bounded message sizes, explicit deadlines, monotonically increasing
observation sequences, and latency-based prefix dropping for stale actions.

If transport, validation, decoding, or server inference fails, the action queue
is cleared and rollout shutdown begins. Teardown disarms both arms, while each
local i2rt worker independently enters idle if its command TTL expires. The
client does not automatically reconnect and resume motion after a failure.
